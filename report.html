1. Introduction & Website Choice

1.1 Project Overview

This project implements a Retrieval-Augmented Generation (RAG) chatbot that answers questions about the pandas Python library by retrieving relevant documentation passages and generating accurate, grounded responses via a large language model. The system combines two retrieval strategies (direct Q&A matching and semantic document search) with a conversational LLM to deliver precise answers with source citations.

1.3 Justification for Choosing pandas Documentation

The pandas User Guide was selected for the following reasons:

  • High query frequency: pandas is among the top 5 most-used Python packages. Developers constantly look up API usage, which makes a domain-specific QA chatbot immediately useful.
  • Structured content: Sphinx-generated HTML has a consistent layout (headings, code blocks, parameter tables), which simplifies extraction of clean, coherent text chunks.
  • Rich knowledge density: Each page contains numerous functions, parameters, and code examples – ideal for generating diverse, specific Q&A pairs.
  • Publicly accessible & legally scrape-able: The pandas documentation is published under the BSD 3-Clause license and permits educational use and reproduction.
  • Factual grounding requirement: Library documentation demands precise, factual answers (e.g., parameter names, return types), making it a good test of RAG over hallucination-prone free-form LLM generation.

The scraper (src/scraper.py) uses requests for HTTP fetching and BeautifulSoup 4 with the lxml parser for HTML parsing. The pipeline is:

  1. Iterate over a predefined list of 23 target URLs from config.py.
  2. Fetch each page with a polite User-Agent header identifying the bot.
  3. Parse the page and remove non-content elements (navigation, footer, sidebar, search box).
  4. Extract the main article content using PyData Sphinx Theme selectors.
  5. Clean and normalise whitespace, then save as a plain .txt file with a metadata header.
  6. Wait SCRAPE_DELAY = 2 seconds between requests to respect the server.

2.2 HTML Cleaning Strategy

The pandas documentation uses the PyData Sphinx Theme. Content is inside div.bd-content or article.bd-article. The scraper removes:

  • nav, footer, script, style – structural chrome
  • .headerlink – permalink anchors (¶ symbols)
  • .toctree-wrapper, #searchbox, .sphinxsidebar – navigation panels
  • .bd-sidebar, .bd-toc, .prev-next-area – theme UI elements

After tag removal, get_text(separator="\n", strip=True) extracts clean prose, and excessive blank lines are collapsed to at most one blank line.

Each saved file has a small metadata header:

2.3 Challenges Faced

ChallengeDescriptionResolution
PyData Sphinx Theme selectors The modern PyData theme nests content differently from classic Sphinx. A single CSS selector did not cover all pages. Implemented a cascading selector chain (bd-content → bd-article → main → body) with fallback.
Navigation/sidebar noise Without removing sidebar elements, extracted text contained irrelevant menu items, increasing Q&A noise. Explicit tag.decompose() calls for all non-content elements before text extraction.
Header link artefacts Sphinx inserts ¶ permalink symbols after every heading via .headerlink tags. Removed via CSS selector before text extraction.
Rate limiting / politeness Scraping 23 pages too quickly risks IP blocks and puts unnecessary load on the server. Added 2-second delay between requests and a descriptive User-Agent string.
Large pages (e.g., io.html) Some pages are very long (~60,000 characters), producing too many chunks for fast Q&A generation. Chunking at Q&A generation time (max 1,500 chars per chunk) rather than at scrape time.

3. Q&A Generation Prompt Strategy

3.1 Overview

The Q&A generator (src/qa_generator.py) converts raw scraped text into structured question-answer pairs using a locally running LLM. It operates in a fully offline, rate-limit-free manner using Ollama with the llama3.2:3b model.

3.2 Model Choice

Model: llama3.2:3b via Ollama (local inference)
Reason: The larger llama3.1:8b requires 4.8 GB RAM but only 4.5 GB was available on the development machine. The 3B model (2 GB) fits comfortably and still produces coherent JSON-structured Q&A pairs. It runs entirely offline – no API keys, no rate limits, no cost per token.

3.3 Prompt Design

The prompt instructs the model to act as a dataset generator and enforces strict JSON output:

You are a Q&A dataset generator for a RAG chatbot about the pandas library.

Given the text below, generate exactly {n} question-answer pairs that test
real comprehension.
- Questions must be specific and answerable from the text only
- Answers must be concise but complete (2-4 sentences)
- Cover different aspects of the text (don't repeat similar questions)

Return ONLY a valid JSON object with a "pairs" key containing an array.
No explanations, no markdown, no preamble.

Format:
{"pairs": [
  {"question": "...", "answer": "..."},
  ...
]}

TEXT:
{chunk}

3.4 Chunking Strategy

Before passing content to the LLM, each page is split into chunks of max 1,500 characters. The chunking algorithm:

  1. Splits on double newlines (paragraph boundaries) first.
  2. If a single paragraph exceeds 1,500 chars, splits further by sentence ((?<=[.!?])\s+ regex).
  3. Filters out chunks shorter than 100 characters (too short to generate meaningful pairs).

Each chunk produces 5 Q&A pairs. This balances diversity (multiple pairs per topic) with speed (smaller context = faster inference on CPU).

3.5 JSON Robustness

Small models occasionally produce slightly malformed JSON (e.g., trailing commas, truncated strings). The parser handles this with:

  • Markdown fence stripping: Removes ```json / ``` wrappers if the model adds them.
  • Retry logic (max 2 retries): On JSON parse failure, the same chunk is retried up to 2 more times.
  • Graceful skip: After 3 failed attempts, the chunk is skipped with a log message; processing continues.
  • Field validation: Only pairs with both "question" and "answer" keys are kept.

3.6 Deduplication

After all pages are processed, a deduplication pass removes pairs with identical (case-insensitive) questions. This eliminates near-duplicate pairs that arise when similar content appears in multiple sections of the documentation.

5. Hybrid Retrieval Explanation

5.1 Motivation

A RAG system must balance two goals: precision (returning the exact right answer) and coverage (handling questions not in the Q&A dataset). Pure Q&A matching is fast and precise but fails on novel phrasing. Pure document search is flexible but forces the LLM to synthesise answers from long contexts, risking hallucination.

The hybrid approach implemented here uses a threshold-based decision gate: if the user's question closely matches a known Q&A pair, return the pre-validated answer directly. Otherwise, fall back to semantic document retrieval and LLM generation.

5.2 Two-Store Architecture

Two separate ChromaDB collections are maintained:

StoreCollection NameContentEmbedding
QA Store pandas_qa Questions from Q&A dataset (answers stored as metadata) all-MiniLM-L6-v2
Doc Store pandas_docs Raw documentation chunks (500 chars, 50 overlap) all-MiniLM-L6-v2

5.3 Retrieval Decision Logic

User Query │ ▼ QA Store → similarity_search_with_relevance_scores(query, k=1) │ ├─── score ≥ 0.75 ───► Return pre-stored answer directly │ (mode = "qa_match") │ Fast, no LLM call needed │ └─── score < 0.75 ───► Doc Store → similarity_search(query, k=5) Retrieve top-5 chunks Build context prompt Groq LLM generates answer (mode = "doc_search")

5.4 Threshold Choice (0.75)

The threshold of 0.75 cosine similarity was set based on empirical testing with all-MiniLM-L6-v2 embeddings:

  • A score above 0.75 reliably indicates the user's phrasing matches a known question closely enough that the stored answer is correct and complete.
  • Below 0.75, the match is too uncertain and the LLM-generated answer (with fresh document context) is safer.
  • The threshold is configurable via HYBRID_THRESHOLD in config.py.

5.5 Embedding Model

sentence-transformers/all-MiniLM-L6-v2 was chosen as the embedding model:

  • Compact (80 MB) – fast to load and run on CPU
  • 384-dimensional dense vectors – good quality for semantic search
  • Runs fully locally – no external API call for embeddings
  • Well-supported by LangChain's HuggingFaceEmbeddings wrapper

5.6 Conversation Memory

The chatbot maintains a rolling window of the last 6 conversation turns (configurable via MAX_HISTORY_TURNS). Previous turns are included in the LLM message list to allow follow-up questions. Memory is stored in-process (not persisted to disk) and can be reset via the "Clear Chat" button in the UI.

7. Limitations & Future Improvements

7.1 Current Limitations

LimitationImpactSeverity
Static dataset (no live updates) If pandas releases a new version, the chatbot's knowledge does not update automatically. Answers may become outdated. Medium
CPU-only inference (Q&A gen) Generating Q&A pairs with llama3.2:3b on CPU is very slow (~1–3 min per page). A GPU would reduce this by 10–20×. High (dev time)

Fixed threshold (0.75) The hybrid threshold was set manually. For some query types (e.g., code-heavy questions), a different threshold may be optimal. Low
No reranking The doc store returns the top-5 chunks by cosine similarity with no further reranking, which may not always be the most relevant 5 passages. Low–Medium
In-memory conversation history Chat history is lost on page refresh or server restart. No persistent sessions. Low

8. Learnings

8.1 Technical Learnings

RAG System Design

Building this chatbot made clear that data quality is the dominant factor in RAG system quality. The scraping and Q&A generation pipeline spent more time and effort than the chatbot itself. Clean, well-structured documents produce better embeddings and more relevant retrievals.

Hybrid Retrieval Value

The two-store hybrid approach proved its value early in testing. For frequently asked, textbook questions (e.g., "How do I read a CSV?"), the QA store returns a polished, pre-validated answer in milliseconds without an LLM call. For complex or novel questions, the doc store + LLM path provides flexible, context-grounded answers. Neither approach alone would have been as effective.

LLM Quirks with JSON Output

Small language models (3B parameters) are inconsistent at producing valid JSON under complex prompts, especially when the context chunk contains code blocks or special characters. Key lessons:

  • Always implement retry logic with a clear error log – silent failures lose data.
  • Markdown fence stripping is essential since models often wrap JSON in ```json blocks.
  • Reducing the number of requested pairs (from 8 to 5) and chunk size (from 3,000 to 1,500 chars) significantly improved JSON reliability.

API Rate Limits

Working with free-tier LLM APIs (Groq: 6,000 TPM) on a dataset generation task is impractical without careful rate management. The pivot to local Ollama inference for Q&A generation eliminated rate limits entirely, at the cost of much slower throughput. The key insight is: use local models for batch offline tasks, cloud APIs for interactive online tasks.

Embedding Model Selection

all-MiniLM-L6-v2 is a pragmatic choice: small enough to run comfortably on CPU, yet high enough quality for semantic similarity search within a narrow technical domain. For production systems, a domain-specific code-aware embedding model (e.g., CodeBERT derivatives) might yield better results for documentation with many code examples.

8.2 Process Learnings

  • Start with a working scraper before designing the LLM pipeline. Data quality issues in raw text (noise, structure problems) compound through every downstream step.
  • Test each pipeline stage independently (scraper → Q&A gen → vector store → retriever → chatbot) before integrating, rather than building everything first and debugging end-to-end.
  • Version control from the start. Pushing to GitHub immediately ensured no work was lost during debugging sessions and made rollbacks easy.
  • Centralise configuration. Having a single config.py file made switching between models, paths, and hyperparameters trivial.
  • RAM constraints are real engineering constraints. The inability to run llama3.1:8b locally (4.8 GB needed, 4.5 GB available) forced a creative solution (use the 3B model for generation, use the cloud API for inference) that turned out to be a better architectural choice anyway.
